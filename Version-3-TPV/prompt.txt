# PROYECTO: SISTEMA DE PEDIDOS POR QR + TPV/COCINA EN TIEMPO REAL

Quiero que desarrolles desde cero una aplicación web completa para un establecimiento de restauración.

La aplicación tendrá dos partes principales:

1. **INTERFAZ CLIENTE**

   * Se utiliza principalmente desde teléfonos móviles.
   * El cliente escanea un código QR situado físicamente en una mesa.
   * Puede consultar la carta.
   * Selecciona productos y cantidades.
   * Puede añadir notas especiales.
   * Envía el pedido.
   * Puede seguir realizando nuevos pedidos mientras la mesa siga abierta.

2. **PANEL TPV / COCINA / ADMINISTRACIÓN**

   * Se utiliza desde tablet, ordenador o portátil.
   * Tiene una interfaz estilo TPV, optimizada para pantallas táctiles.
   * Recibe automáticamente los pedidos realizados por los clientes.
   * Los pedidos deben aparecer en tiempo real sin necesidad de recargar la página.
   * Permite gestionar el estado de los pedidos.
   * Permite ver la mesa, productos, cantidades, notas y hora del pedido.
   * Permite marcar pedidos como entregados.
   * Mantiene el historial de pedidos de una mesa para poder calcular la cuenta final.
   * Permite cerrar una mesa.
   * Permite dividir la cuenta.

---

# 1. TECNOLOGÍAS OBLIGATORIAS

Utiliza:

* Vue 3
* Vite
* JavaScript o TypeScript, preferiblemente TypeScript si no complica innecesariamente el proyecto.
* Vue Router
* Firebase
* Firebase Authentication para la zona administrativa.
* Firebase Firestore como base de datos principal.
* Firebase Storage si se necesitan imágenes de productos.
* Firebase Hosting para poder desplegar el proyecto.
* CSS moderno y responsive.
* No utilizar frameworks excesivamente complejos si no son necesarios.

El proyecto debe poder ejecutarse fácilmente con:

```bash
npm install
npm run dev
```

Y posteriormente:

```bash
npm run build
```

Debe estar preparado para subirlo a GitHub y desplegarlo fácilmente mediante Firebase Hosting o GitHub.

NO quiero un backend tradicional separado si Firebase permite resolverlo correctamente.

Si alguna operación necesita privilegios de servidor, utilizar Firebase Cloud Functions en lugar de exponer credenciales o lógica sensible al cliente.

# 6. MESAS

Cada mesa debe tener:

```text
id
number
name
active
qrIdentifier
currentSessionId
createdAt
updatedAt
```

Ejemplo:

```text
Mesa 1
Mesa 2
Mesa 3
...
Mesa 40
```

El sistema debe poder soportar muchas mesas, no solamente 40.

Cada mesa tiene un QR físico.

IMPORTANTE:

El QR NO debe contener una sesión permanente.

El QR debe identificar únicamente la mesa.

Por ejemplo:

```text
https://dominio.com/mesa/ABC123
```

donde `ABC123` identifica la mesa.

---

# 7. SISTEMA DE SESIONES Y SEGURIDAD DEL QR

Esta es una de las partes MÁS IMPORTANTES del proyecto.

No quiero que una URL de cliente pueda utilizarse indefinidamente.

Cuando alguien escanea el QR de una mesa:

```text
/mesa/:qrIdentifier
```

el sistema debe comprobar la mesa y crear o recuperar la sesión activa correspondiente.

La sesión debe tener:

```text
sessionId
tableId
token
createdAt
expiresAt
active
closedAt
```

El token debe ser aleatorio, impredecible y suficientemente largo.

Ejemplo conceptual:

```text
/pedido/a8f7c1d92e84f7...
```

La URL real debe ser diferente cada vez que corresponda crear una nueva sesión/token.

---

# 8. DURACIÓN DE LA SESIÓN

Cada sesión debe tener una duración máxima de:

**3 HORAS**

Guardar:

```text
createdAt
expiresAt
```

El frontend debe comprobar que la sesión no esté caducada.

Si la sesión ha caducado:

* No permitir nuevos pedidos.
* Mostrar un mensaje indicando que la sesión ha expirado.
* Permitir volver a escanear el QR para crear/obtener una sesión válida.

IMPORTANTE:

La sesión de mesa debe poder seguir agrupando diferentes pedidos realizados durante esas 3 horas.

Por ejemplo:

12:00 → cliente pide cafés.

12:30 → pide bocadillos.

13:00 → pide bebidas.

Todo debe pertenecer a:

```text
Mesa 5
Sesión X
```

y aparecer posteriormente en la misma cuenta.

---

# 9. EVITAR CONFLICTOS ENTRE CLIENTES

Puede haber varios clientes en la misma mesa.

No quiero que cada cliente tenga una cesta completamente independiente que haga que los pedidos se pierdan o se mezclen incorrectamente.

Todos los pedidos deben estar asociados a:

```text
tableId
sessionId
```

De esta forma:

```text
Mesa 5
   └── Sesión X
       ├── Pedido 001
       ├── Pedido 002
       ├── Pedido 003
       └── Pedido 004
```

Cada pedido tendrá su propio `orderId`.

Si varias personas hacen pedidos desde la misma mesa, todos se acumulan en la sesión.

---

# 10. PROBLEMA DEL TOKEN DESPUÉS DE CERRAR LA MESA

Esto también es MUY IMPORTANTE.

Imagina:

Una persona está sentada en la Mesa 8.

Escanea el QR.

Obtiene:

```text
/pedido/abc123
```

Después de terminar la comida, el camarero cierra la mesa.

La persona podría intentar utilizar posteriormente:

```text
/pedido/abc123
```

para realizar otro pedido.

Esto NO debe funcionar.

Cuando el TPV cierre la mesa:

```text
session.active = false
session.closedAt = fecha
```

Todos los tokens asociados a esa sesión deben quedar invalidados.

Si alguien intenta acceder posteriormente mediante una URL antigua:

```text
/pedido/abc123
```

debe aparecer:

```text
Esta sesión ha finalizado.

Escanea nuevamente el código QR de tu mesa para comenzar una nueva sesión.
```

No permitir realizar pedidos.

---

# 11. NUEVA SESIÓN DESPUÉS DE CERRAR LA MESA

Cuando una mesa se haya cerrado:

```text
Mesa 8
Sesión antigua → CERRADA
```

Cuando posteriormente alguien vuelva a escanear el QR:

```text
Mesa 8
Nueva sesión → ACTIVA
```

Esto debe comenzar una nueva cuenta completamente independiente.

Los pedidos anteriores deben mantenerse en la base de datos como historial, pero NO formar parte de la nueva cuenta.

---

# 12. IMPORTANTE SOBRE ESCANEOS MÚLTIPLES

Diseña el sistema de forma que varios clientes puedan escanear el QR de la misma mesa durante una sesión activa.

Todos deben terminar asociados a la misma:

```text
tableId
sessionId
```

No crear una cuenta independiente por cada persona.

Sin embargo, cada acceso puede tener un token de cliente diferente si resulta necesario para seguridad.

La arquitectura debe diferenciar claramente:

```text
MESA
SESIÓN DE MESA
ACCESO/TOKEN DE CLIENTE
PEDIDO
```

Ejemplo:

```text
Mesa 10
│
└── Sesión 2026-001
    │
    ├── Cliente/token A
    │      └── Pedido 1
    │
    ├── Cliente/token B
    │      └── Pedido 2
    │
    └── Cliente/token C
           └── Pedido 3
```



# 31. CUENTA DE LA MESA

La cuenta debe sumar TODOS los pedidos válidos de la sesión.

Ejemplo:

```text
MESA 5

Pedido #1     8,50 €
Pedido #2     4,00 €
Pedido #3     12,50 €
Pedido #4     3,00 €

--------------------

TOTAL
28,00 €
```

Los pedidos entregados continúan formando parte del total.

Los pedidos cancelados NO deben sumar.

---

# 33. DIVIDIR CUENTA

La cuenta debe permitir diferentes métodos.

## OPCIÓN 1: UNA SOLA PERSONA

```text

```

---

## OPCIÓN 2: DIVIDIR A PARTES IGUALES

El empleado selecciona:

```text

[ - ] 4 [ + ]
```

El sistema calcula:

```text
28,00 € / 4

Persona 1: 7,00 €
Persona 2: 7,00 €
Persona 3: 7,00 €
Persona 4: 7,00 €
```

# 37. RESET DEL QR / SESIÓN

Cuando la mesa se cierre:

```text
currentSessionId = null
```

y la sesión anterior:

```text
active = false
```

Todos los accesos asociados a ella dejan de funcionar.

El QR físico no necesita cambiar.

Esto es MUY IMPORTANTE:

El QR de la mesa puede permanecer físicamente en la mesa durante años.

Lo que cambia es la sesión interna.

Ejemplo:

```text
QR Mesa 5
    ↓
Sesión A
    ↓
Cerrar mesa
    ↓
Sesión A INVALIDADA
    ↓
Nuevo escaneo
    ↓
Sesión B
```

# 64. FLUJO COMPLETO DEL CLIENTE

Implementar exactamente este flujo:

```text
1. Cliente escanea QR.

2. Aplicación identifica la mesa.

3. Comprueba si existe una sesión activa.

4. Si no existe:
   crea una nueva sesión.

5. Si existe:
   permite acceder a la sesión activa.

6. Genera/gestiona el acceso seguro correspondiente.

7. Cliente entra en la carta.

8. Selecciona categoría.

9. Selecciona productos.

10. Añade cantidades.

11. Añade notas.

12. Abre carrito.

13. Comprueba total.

14. Confirma pedido.

15. Firebase registra el pedido.

16. TPV recibe automáticamente el pedido.

17. Cocina lo prepara.

18. Cocina cambia el estado.

19. Camarero lo entrega.

20. Pedido queda como ENTREGADO.

21. El pedido continúa dentro de la cuenta de la mesa.

22. Cliente puede volver a pedir.

23. Se crean nuevos pedidos dentro de la misma sesión.

24. Cliente termina.

25. Camarero abre cuenta.

26. Selecciona método de división.

27. Registra pagos.

28. Cierra mesa.

29. Sesión pasa a inactiva.

30. Tokens anteriores quedan invalidados.

31. Mesa queda libre.

32. El siguiente cliente vuelve a escanear el mismo QR.

33. Se crea una nueva sesión.
```

# 65. FLUJO COMPLETO DEL TPV

```text
1. Empleado inicia sesión.

2. Accede al TPV.

3. Ve las mesas.

4. Una mesa recibe un pedido.

5. Aparece automáticamente.

6. Se muestra:
   - Mesa
   - Hora
   - Productos
   - Cantidades
   - Nota
   - Total

7. Cocina pulsa PREPARANDO.

8. Cocina pulsa LISTO.

9. Camarero pulsa ENTREGADO.

10. El pedido permanece en la cuenta.

11. Cliente puede hacer otro pedido.

12. Aparece otro pedido.

13. Al terminar la mesa:
    abrir cuenta.

14. Ver todos los pedidos.

15. Ver total.

16. Dividir cuenta.

17. Registrar pagos.

18. Cerrar mesa.

19. Invalidar sesión.

20. Mesa vuelve a estar libre.
```
